## Reproduce and limits

Source the prepared `implementation/K-09/local-2026-10-23/env.sh`, then run
`scripts/frost-lifecycle-local.sh <new-evidence-directory>` with matching paired
worktrees. The runner uses pinned SNOWFALL worker, Bitcoin Core and native digest
binary, local unforked Hardhat, sequential stages, 8 Go cores, 8 GiB Node heap
(16 GiB compilation), 900 seconds per stage and a 14-minute Go timeout.
No Docker or CI is involved. Core/tss-lib jobs run alone.

There are 14 required stages: two compilations, full deployment artifact binding,
runner controls, config controls, build, six Go stages, and two contract stages.
Eight named Go cases and 20 contract cases must pass without skips. The joined
case must emit all ten ordered checkpoint markers exactly once. Fifteen runner
probes include thirteen focused owning-assertion controls; these are not the
final mutation campaign. `--only` always reports partial acceptance.

The source manifest hashes the whole Go module, recursively resolved local
replacements, and actual `go list -deps -test` source/native/embed inputs.
The artifact manifest binds every shared native deployment root (including
package proxies, pools and proposal validator), ABI and linked library to its
compiler input/output and all current imported sources. Both manifests must
remain identical at the end. Post-commit correspondence maps those exact bytes
to committed heads without reusing a partial run as final acceptance.

Raw diagnostics and generated legacy witnesses stay in a separate 0700 private
directory under umask 077. Public evidence is generated status/provenance only.
A supplementary detector refuses recognized forbidden output; it does not
certify diagnostics safe to publish. Never decode or export opaque records.

## Joined witness and crash bound

One deployment carries two distinct real DKG wallets through deposit credit,
redemption, heartbeat, authenticated inactivity, cutover, containment, movement,
incoming sweep, public fraud challenge, restarted defense and closure. Both
in-process operator bundles reload wallet keys. The test directly checks the
contract closure guard and exact cutover/containment rejection reasons with
unchanged financial/custody/obligation frames. A third real DKG succeeds after
FrostOnly cutover. The harness mines only within a bounded context for that DKG.

The restart includes SIGKILL of a child process while its real journal signing
claim is active. After death, the same store rejects reuse of that claim and
accepts a fresh claim; the joined defense then consumes the reopened durable
record before the public deadline. The parent-controlled fence survives and
explicitly revokes the dead holder; this is not host power-loss or production
fence qualification. Local policy values (three seats, threshold two, finality
two blocks, ten-block round and one-second closing period) remain OPEN inputs.
The offline-refund case removes signing resources before constructing a refund.

## Upgrade, proof policy and coverage limits

Public 76f7905 fixtures carry real legacy obligations across actual proxy
upgrades without seeding Bridge/Bank storage. Thirteen public upgrade/reconciliation
cases cover deposit, redemption settlement/timeout, fraud defense/timeout,
outgoing/incoming proof and timeout, source closing and watchtower state.
The original incoming replay with current main reaches the input-count guard;
an isolated seeded production-library control separately reaches the consumed
request-state guard with a successful pending-request witness. Duplicate
discharge preserves the state frame; a redeemer/notifier alias uses
the original deadline and exact refund. This is bounded adversarial coverage.

`legacy-drain` uses real tss-lib ECDSA and Core bytes but its legacy state is
seeded. It is a **seeded component control**, not a public legacy obligation
joined through upgrade, cutover and containment into FROST.

Six realistic-header tests exercise the production BitcoinTx library at the
mainnet factor; they are not a full realistic FROST entry-point witness. Live
regtest has zero integer relay difficulty. The FROST redemption CLI now installs
the same difficulty-aware proof-depth calculation as the legacy maintainer;
`--confirmations` is an additional floor. Rising/falling retarget, DIFF1,
insufficient work and relay-range cases exercise the actual FROST producer's
chosen assembly count using a test assembler. Component callers may explicitly
retain fixed regtest counts. No live production relay is qualified here.
