## Reproduce

Use `scripts/frost-lifecycle-local.sh <new-evidence-directory>` with the matching
K-09 tbtc-v2 worktree, Anvil, reviewed SNOWFALL worker and Bitcoin Core 29.0.
The environment used here is
`implementation/K-09/local-2026-10-23/env.sh` in the integration workspace.
Bitcoin Core and bitcoin-cli are retained under `implementation/K-09/tools`,
outside `/private/tmp`. Dependencies come from the existing lockfiles.

The script compiles the contract worktrees, binds production artifacts to
compiler inputs/outputs and current sources, enforces EIP-170, builds keep-core,
then runs the named stages sequentially. It never invokes the final mutation
campaign. Every command stage has a 900-second wall limit; Go cases also have a
14-minute timeout. GOMAXPROCS is 8; Node heap is 8 GiB (16 GiB for compilation).
Run limits and commands precede execution in `result.json`. No CI or Docker.

`--only <stage>` is a scoped diagnostic and reports `partial`, never complete
acceptance. Required Go cases must each report exactly one pass with no skips.
Contract cases use a JSON reporter and require the exact expected case count,
zero pending and zero failures. A failed command or harness outage is an error.

## Joined witness

`TestFrostCompleteLocalLifecycle` uses one deployment, two distinct real DKG
wallets and two real operators with three seats (one operator holds two).
Every operator reloads each wallet key. A Core-funded deposit is threshold
swept and credited once. A redemption consumes that main; its proven change
is the main consumed by the subsequent movement.

A guarded successful heartbeat precedes two failed rounds with authenticated
seat-3 absence. A threshold inactivity claim starts movement. DKG switches to
FrostOnly; a rejected new legacy request leaves its relevant state unchanged.
Containment remains active while the source commits to wallet B, signs,
broadcasts and proves its movement, and B signs and proves its incoming sweep.
Value is conserved apart from the recorded fees.

The actual movement signature is challenged publicly. Closure refuses it
without changing custody, credits or obligations. One operator closes and
reopens its store; the defender uses only its durable record and the chain,
and resolves the challenge before its public deadline. A closes with no
obligations. B retains 900,266 sats; both wallets' keys remain loadable on both
operators. The local closing period is one second (D-09 OPEN) so this witness
can check matured closure and a defense before the fraud deadline together.

The offline refund witness disconnects operator peers, closes their stores
and removes their worker executables after reveal. It constructs the refund
only then, refuses it before locktime, mines it after locktime, and checks zero
worker launches, no deposit sweep and no Bank credit. The harness's network
objects can still exist; the signing resources required by an operator do not.

## Upgrade and SPV witnesses

No Bridge/Bank storage writes create the legacy upgrade precursors. The
76f7905 baseline publicly registers a wallet, reveals and credits real Core
funding, and creates actual redemption/watchtower records. Separate reachable
checkpoints retain an unswept deposit/open fraud challenge, an outgoing
commitment, and an incoming sweep across actual proxy upgrades. Original
slots 0..128 and the financial/obligation frames are preserved. Real Core
transactions complete both sides of the movement (99,000 -> 98,000 -> 97,000
sats), and duplicate discharge is refused. The existing witness retains and
mines the identical pre-upgrade signed redemption bytes.

The SPV run uses retained mainnet headers and production BitcoinTx validation
with difficulty 7,019,199,231,177 and the mainnet deployment factor six. Six
headers pass; five fail for insufficient accumulated work. Bad links, bad
per-header work and incorrect transaction/coinbase inclusion fail at their
own guards. The relay epoch observation is controlled; relay deployment and
canonical-chain qualification remain outside this test.
