# Local K-05 acceptance

Run `test/frost/run-k05.sh <evidence-directory>`. Use the K-04 environment from
`K04.md`. `FROST_K03_TBTC` must point at a compiled tbtc-v2 worktree holding the
C-04 stack (C-07, C-05, C-04) plus the K-05 TypeScript change, with its
`solidity` and `typescript` dependencies installed from their locks. The script
fails if a required variable is missing. A direct Go run skips the external
fixture when its dependencies are absent, and that skip does not establish K-05.

## What the fixture does

`newK05World` deploys the real contracts in `deploy.cjs` `k05` mode: the Bridge
proxy, a real Bank, the zero-difficulty regtest relay test contract and the
prototype C-07 verifier, with FROST funding and redemptions enabled. It then:

1. Runs a real 1/1/2 DKG with the hash-pinned worker, through public approval to ReadyUnfunded.
2. Funds custody through the actual C-05 path:
   - deposits to the Bridge's own deposit construction;
   - reveals the deposit;
   - sweeps it with a real threshold BIP342 signature, which Core accepts;
   - proves the sweep by SPV.

   The wallet becomes Live with recognized main custody.

**The sweep signature is test-only.** It uses the unguarded K-01 engine. K-06 owns the authorized host sweep path.

Every K-05 step afterwards uses production code on each operator's real encrypted store and worker:

| Step | Code |
| --- | --- |
| Discovery and planning | `redemption.Planner`, `tbtcpg.ProposeFrostRedemption` |
| Attestation (fresh-worker key reload first) | `redemption.Attester` |
| C-04 admission | `FrostRedemptionChain.Reserve` |
| Chain-derived agreement and signing | `redemption.Resolver` with the K-04 executor |
| Rebroadcast and cancellation | `redemption.Resolver` |
| SPV settlement, timeouts and refunds | `spv.FrostRedemptionMaintainer` |

## Named tests

| Test | Acceptance check |
| --- | --- |
| `TestFrostRedemptionLifecycle` | Two funded requests are discovered from logs and planned independently and deterministically. Every operator attests after a key reload; C-04 admits; one real worker launch per input; Core mines; the maintainer proves and the intent is Paid. SC-05: each output equals gross − treasury fee − capped share; shares sum to the fee; main = payouts + fee + change; custody, state version and generation advance; escrow and liability return to zero; treasury, Bridge and redeemer Bank frame. Proof replay, refunds and timeout of paid requests refuse. The next slot (generation 2, version 2) settles. |
| `TestReservationTimeoutRace` | Five cases. **Before reservation:** no plan; notice; refund refused before finality and allowed after. **After reservation:** no worker launch and no refund; cancellation proven, then full refund. **After share release:** the timeout lands after every Done record is durable; both operators quarantine; nothing reaches Bitcoin; cancellation, then refund. **After signing:** `AlwaysCancel` does not broadcast and an ordinary broadcast refuses; `RebroadcastThenCancel` rebroadcasts the accepted result; the historical payment settles in TimeoutPending; refunds refuse. **Unmined payment:** the payment is rebroadcast inside the window and stays in the mempool; once the chain-derived window passes every operator moves to cancellation; the cancellation replaces the payment in the mempool, confirms, and the request is refunded. **After broadcast:** the payment proves in TimeoutPending; refunds and a later cancellation attestation refuse. |
| `TestLateSignatureQuarantine` | The late signature is durably quarantined and a possible release is recorded. Broadcast refuses. A second release is refused with no worker launch. Only a proven cancellation refunds. The quarantined payment can never be proven afterwards. |
| `TestContainedReservationNeedsDirective` | Governance contains the wallet (C-04 `Quarantined`) after a timely payment was signed. No host rebroadcasts or cancels on its own, and the attester refuses a cancellation (`ErrContained`), until a governance directive names the containment class and the action. With a cancel directive the reservation is cancelled and refunded. |
| `TestZeroNetAndFeeBoundaries` | FROST planner, before any plan exists: wrapped treasury fee, zero or negative net, share above the captured cap, dust, satoshi-domain overflow, fee-rate and fee domain, governance total cap, insufficient change, main not discoverable by script, deadline margin. Legacy assembler (`pkg/tbtc`): wrapped, zero and negative nets, negative share, overdrawn main UTXO. |

Review fixes (Astra review, 15 October 2026), each with a regression test that fails when its fix is reverted:

| Finding | Fix | Regression |
| --- | --- | --- |
| P1: non-final cancellation | Payment and cancellation transactions must be immediately final: no BIP68 relative lock, and absolute locktime zero or disabled by final sequences. `signing.ImmediatelyFinal` enforces this in `NewCancellationPlan` and `Planner.Validate`. | `TestCancellationPlanRequiresImmediateFinality` |
| P2: dust change | `Validate` refuses dust or non-final supplied plans; `AttestCancellation` refuses a dust output. | `TestValidateRefusesDustChangeAndNonFinalPlans`, `TestAttestCancellationRefusesDustOutput` |
| P2: lost signed marker | A `sign-attempt` round marker is written before `Run`. A missing signed marker is reconciled from the durable executor result. `Resolve` waits for the next round instead of reusing a terminal attempt. | `TestSignedResultRecoveredWithoutLedgerMarker` (real fixture; marker write fails on both operators; Reserved and timed-out cases) |
| P2: ledger saturation (re-review) | Ledger and attestation history reads are unbounded. Appends stop at 4,096. The last 512 slots accept only recovery records: timeout and escalation, cancellation attestation, attempt, signature and broadcast, payment signed and broadcast, late quarantine, outcome. Ordinary records (payment attempts, possible release) stop before the reserve. Cancellation attempts have their own kind. Beyond the full capacity the ledger fails closed. | `TestLedgerCapacityKeepsHistoryReadable`; `TestLedgerRecoveryHeadroom` (real timeout resolution, cancellation attestation, signing, broadcast, proof and refund with ordinary space exhausted; fails with "ledger capacity reached for timeout-seen record" when the prerequisites are not reserved) |

Unit tests in `pkg/frost/redemption`:

- planner validation against stale chain state;
- the attestation slot lock: idempotent statement, renewal, refusal before finalized deadlines, refusal of an admitted slot, replacement after finalized non-admission, retained history, signature recovery;
- the chain-derived agreement (round, reorg and purpose separation);
- one consistent canonical read;
- the append-only ledger;
- seat collection;
- the ABI request-ID hash.

The TypeScript unit tests are in `tbtc-v2/typescript/test/services/frost-redemptions.test.ts`.

Two policy questions are also still open:

- Spec issue tlabs-xyz/FROST-migration-spec#3 is resolved: `RebroadcastThenCancel`, rebroadcasting a timely signed payment only within a chain-derived window, then cancelling. A cancellation checks its prevouts against confirmed chain state, so the payment it replaces may sit in the mempool. D-08 must still decide the post-deadline promise to users ("refund", or "exactly one of BTC or refund").
- `Quarantined` is separate (spec issue #3): hosts act only on a governance directive naming the containment class, because they see only C-04's `reasonHash`. How a host authenticates a directive is OPEN.
- Spec issue #2 (A5) is resolved: historical SPV settlement of the exact admitted payment stays allowed; the host never broadcasts a late signature.

## Not covered

- The production fence, storage class and canonical archive provider.
- Cross-operator certificate transport. The tests collect certificates in process.
- Fee and inclusion escalation above the captured envelope (`A-FEE-INCLUSION-ESCALATION`).
- Reorganizations beyond the canonical-hash checks.
- Executed power loss.

V-04 replay status is recorded separately.
